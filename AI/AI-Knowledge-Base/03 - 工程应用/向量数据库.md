## 一句话本质

**专门的数据库，存向量、算距离、快搜索。**

```
普通数据库（MySQL）：存行和列 → 搜索靠关键词匹配
向量数据库（FAISS）：存向量 → 搜索靠距离计算
```

---

## 为什么需要向量数据库

```
100 万篇文档，每篇转成 768 维向量

暴力搜索：逐条算距离 → 100 万次计算 → 几百毫秒起步，太慢
ANN 搜索：建索引 → 只查索引指向的一小批 → 几十次计算 → 几毫秒
```

---

## ANN 搜索的核心：HNSW 算法

**HNSW = Hierarchical Navigable Small World（分层可导航小世界图）**

### 原理

```
把 100 万个向量组织成"多层地图"：

第 3 层（最顶层）：只有几个"地标"向量
     ↓
第 2 层：几十个"区域中心"
     ↓
第 1 层（最底层）：全部 100 万向量

搜索时：
  从顶层进入 → 找到最近的地标 → 下到第 2 层
  → 找到最近的区域 → 下到底层 → 找到最近的点
  
全程只比较了几十个向量，不是 100 万个。
```

### 降维映射

```
暴力搜索 = 去 100 万人的城市找一个人，挨个敲门问 → 100 万次敲门
HNSW    = 先飞到城市上空看全景 → 锁定在哪个区
          → 降到区里问路人 → 锁定哪条街
          → 到那条街上找门牌号 → 只问了 50 个人
```

### 精度 vs 速度的 tradeoff

```
参数 ef_search：
  = 10  → 非常快（但可能错过最相关的文档）
  = 200 → 比较慢（但几乎不会错过）
  
生产常用值：100-200 之间
```

## 检索用的 Embedding 和 LLM 的 Embedding 不同

```
LLM 的 Embedding（4096 维）：
  → 用来做推理，不是专门为搜索优化

检索专用的 Embedding（768/1024 维）：
  → 专门训练来做"语义匹配"
  → BGE / text-embedding-3-small / gte-Qwen2
  → 输入：文本 → 输出：固定长度向量

两者模型不同、维度不同、训练目标不同，不能混用。
```

## 🧪 摸底自测

#### Q1（入门）
> 向量数据库和普通数据库（MySQL）的核心区别是什么？

<details>
<summary>解答</summary>

MySQL 存行和列，搜索靠关键词匹配（WHERE name = 'xxx'）。向量数据库存向量，搜索靠距离计算（找最相似的向量）。
</details>

#### Q2（进阶）
> HNSW 怎么做到不用逐条比较就能找到最相似的向量？

<details>
<summary>解答</summary>

HNSW 把向量组织成多层图：顶层只有几个地标，底层有全部向量。搜索从顶层开始逐层下钻，每层只比较几十个向量，而不是全部 100 万个。
</details>
